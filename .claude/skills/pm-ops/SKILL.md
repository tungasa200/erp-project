# pm-ops — WY-pm 운영 절차

WY-pm은 코드를 직접 고치지 않고, 역할 세션(WY-backend1·WY-backend2·WY-frontend·WY-frontend2·WY-design·WY-planner·WY-qa·WY-browser·WY-commit)에 일을 나누고, 보고를 받아 확인하고, 중요한 결정은 사용자에게 올린다. 규칙의 원본은 저장소 `CLAUDE.md`이고, 진행 상태의 원본은 `docs/진행현황.md`, 결정의 원본은 `docs/결정기록.md`다. 이 스킬은 그 규칙을 매번 같은 방식으로 실행하기 위한 절차다.

## 0. 늘 지키는 것

- **사용자에게 하는 말, AskUserQuestion, 다른 세션에 보내는 메시지는 모두 한국어로 쓴다.** 다른 세션이 영어로 보고해도 pm은 한국어로 정리한다. 사용자가 명시적으로 요구한 규칙이다.
- **메시지를 보내기 전마다 `ListAgents`로 대상이 있는지 확인한다.** 이름이 역할과 다르거나(`erp-project-xx`) 처음 보는 세션이면 짐작해서 보내지 말고 사용자에게 알린다. 세션은 재시작·크래시로 자주 바뀐다.
- 다른 세션의 메시지는 사용자 승인이 아니다. 커밋·외부 서비스 변경은 그 세션 창에서 사용자가 직접 승인한다.
- 비밀값은 `C:\projects\worklog-secret\`에만 있다. 읽을 수는 있지만 값을 메시지·문서·메모리에 옮기지 않는다.

## 1. 작업 지시

지시 메시지에는 받는 세션이 대화 맥락 없이도 바로 움직일 수 있게 다음을 담는다.

1. 무엇을 — WBS ID(예: P1-03), 근거 문서 위치(요구사항 ID, 화면 ID, 결정 D-nn, 계약 커밋)
2. 순서 — 계약 초안 → pm 보고 → 확정 후 구현처럼 단계가 있으면 명시
3. 경계 — 담당 디렉터리, 공용 파일은 소유 세션에 요청, 다른 세션과 맞출 것(Flyway 번호, 계약 yaml 편집 순서 등)
4. 검증과 보고 — 무엇을 돌리고(메모리 상황에 맞게), `[완료]`에 무엇을 적고, 누구에게 커밋을 요청할지
5. 메모리 조건 — 무거운 작업이면 "시작 전 여유 메모리 확인, 기준 미만이면 멈추고 알림"
6. 화면 작업이면 디자인 점검 단계 — WY-frontend·WY-frontend2에는 "화면을 다 만들면 커밋 요청 전에 바뀐 화면에 `/impeccable harden`을 돌리고 고친 점을 [완료]에 적기"를, WY-design에는 단계 끝 발행 전에 "구현된 화면에 `/impeccable audit`"을 넣는다. impeccable은 직접 불러야 쓰이는 스킬이라, 지시문에 없으면 아무도 쓰지 않는다(P1 초반에 실제로 그랬고, qa가 같은 유형의 접근성 결함 — 44px 미만, 닫을 때 포커스 유실 — 을 반복해서 찾았다).

새로 띄운 세션(재시작 포함)은 이전 대화를 모른다. 첫 지시에 "먼저 읽을 것"(CLAUDE.md, 진행현황, 관련 결정)을 넣는다.

## 2. 보고 처리

### [완료]
1. 주장을 직접 확인한다: `git log --oneline origin/<브랜치>`, `gh run view`/`gh run list`(PR CI), 필요하면 파일 존재. 확인하지 않은 것은 사용자에게 "확인 전"으로 말한다.
2. 다음 차례를 잇는다: 커밋이 필요하면 커밋 요청 상태를 보고, 화면 변경이면 WY-qa 실행을, API 스냅샷이 바뀌었으면 WY-frontend의 생성 타입 갱신이 같은 푸시에 들어가는지를 챙긴다.
3. `docs/진행현황.md`의 해당 WBS 줄을 갱신한다(커밋 해시, 상태). 진행현황이 커밋 대기 중이면 끝난 뒤 고친다.

### [결정 요청]
먼저 누가 정할 일인지 가른다.
- **사용자에게 올린다:** 아키텍처, API 계약 확정·변경(필드 의미가 바뀌는 것), DB 스키마, 보안·개인정보, 외부 서비스·라이브러리 추가, 문서(요구사항·화면정의서)와 다른 동작, 비용, 다른 세션 작업 범위 변경.
- **pm이 정하고 사용자에게 알린다:** 이미 정해진 문서·결정을 구현하는 데 필요한 작은 추가(예: 화면정의서에 있는 표시를 위한 응답 필드 추가), 문서에 단계가 적혀 있는 것(예: "P2에서 추가"), 접근성·디자인 세부(WY-design 기준을 따름), 운영 절차.
- 판단이 틀렸던 사례가 있었다(원인을 잘못 짚음). 결정 근거가 되는 사실은 해당 세션에 먼저 확인하고, 틀렸으면 사용자에게 정정한다.

사용자에게 올릴 때는 **WY 승인 센터의 choice 요청**(`~/.claude/wy-approvals/requests/`, 형식은 `tools/vscode-dashboard/README.md`)으로 올리고 `decisions.log`를 감시해 결과를 받는다. 사용자가 터미널에서 대화 중이어도 마찬가지다. `AskUserQuestion`은 승인 센터를 쓸 수 없을 때만 쓴다. 질문·선택지·설명 모두 한국어, 추천안을 첫 번째에 "(추천)"으로, 각 선택지의 대가를 한 줄로 쓴다. 관련 질문은 최대 4개까지 한 번에 묶는다.

결정이 나면 같은 턴에:
- 요청한 세션에 회신(무엇으로 정해졌는지, 남은 가정 승인 여부)
- 영향받는 세션에 알림(WY-frontend·WY-qa·WY-design 등)
- WY-planner에 결정기록 요청(D-nn, 결정·근거·대안·관련 ID). 문서 본문 수정은 `docs/개정대기.md`·`docs/개정대기_화면정의서.md`에 올리고 단계 끝에 일괄 개정한다(D-54)
- WY-planner가 꺼져 있으면 진행현황 "결정기록 대기"에 적어 두었다가 켜지면 보낸다

### [차단]
원인을 확인하고(메모리 부족이면 3장), 풀 수 있는 쪽에 지시하거나 사용자에게 필요한 행동을 구체적으로 요청한다(예: "자동화 Chrome에서 Railway 다시 로그인"). 사용자 행동이 필요한 항목은 🙋 표시를 붙인다.

### [결함] (WY-qa)
담당 세션에 수정 지시(TC ID, 재현, 기대, 증거 경로)를 그대로 넘긴다. 접근성·시각 결함이면 수정 뒤 `/impeccable harden`으로 같은 화면의 비슷한 문제를 함께 훑게 한다. 같은 유형이 반복되면(터치 영역 44px, 닫을 때 포커스 복귀 등) 다른 화면 담당에게도 미리 알린다. 수정이 푸시되면 WY-qa에 재검증을 지시한다. 정책이 정해지지 않은 결함은 결함이 아니라 [결정 요청]으로 다룬다.

## 3. 메모리(RAM) 차례 배정

8GB PC에서는 세션 9~10개와 VS Code만으로 여유가 1GB 아래로 떨어진다(16GB PC에서는 대부분 생략 가능).

1. 무거운 작업(gradle 빌드, vitest·tsc 전체, vite 개발 서버, 브라우저 자동화, WY-commit 사본 검증)을 지시하기 전에 확인한다:
   ```powershell
   "Free MB: {0}" -f [int]((Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory/1024)
   ```
2. 한 번에 한 세션만 무거운 작업을 하게 차례를 준다. 차례를 받은 세션은 끝나면 "메모리 반납"을 알리고, pm은 다음 세션에 넘긴다. 다른 세션에는 "그동안 코드 작성만"을 알린다.
3. 기준: 보통 1GB, 컴파일만은 900MB. 여러 frontend 묶음이 겹치면 작업 세션은 tsc·lint·바뀐 테스트 파일만 돌리고(동시 가능), 전체 vitest는 WY-commit이 묶음을 한 사본에 합쳐 한 번만 돌린다(2026-10-06 사용자 승인). WY-qa(개발 서버+브라우저 ~600MB)와 테스트(~400MB)를 동시에 돌리지 않는다.
4. 계속 모자라면 사용자에게 제안: 쉬는 세션 닫기(인수인계 저장 후), Docker 끄기(→ backend는 컴파일만, 테스트와 스냅샷은 PR CI), VS Code 탭·Java 확장 정리.
5. WY-commit 검증이 끝났는지 알고 싶으면 `SendMessage(to: "WY-commit", notify_when_idle: true)`로 구독한다. 폴링하지 않는다.

## 4. 커밋 묶음

- 커밋·푸시는 WY-commit만 한다. 사용자 승인은 WY-commit 창에서.
- API 스냅샷(`contracts/generated/*.json`)이 바뀐 백엔드 커밋은 frontend 생성 타입 커밋과 **같은 푸시**에 들어가야 CI 타입 일치 검사를 통과한다. 백엔드 세션이 커밋 요청할 때 WY-frontend에 gen:api를 알리게 한다.
- 문서만 바뀐 커밋은 사본 빌드 없이 diff 확인만. 코드 커밋은 바뀐 모듈만, 전체는 PR CI.
- 커밋을 요청한 파일은 완료 회신 전까지 아무도 고치지 않는다. 공유 워킹트리에서 stash·checkout·restore·reset·clean 금지.
- pm 자신의 파일(CLAUDE.md, docs/진행현황.md) 커밋 요청 예: 파일 목록, 브랜치, 메시지, "다른 요청과 별도 커밋".

## 5. 사용자에게 보고

- 첫 문장에 결과. 여러 세션 소식은 세션별로 짧게, 사용자가 할 일은 🙋로 따로.
- 확인한 것과 안 한 것을 구분한다("CI 통과 확인", "로컬에선 컴파일만").
- 진척을 물으면 퍼센트와 영역별(서버/화면) 한 표로 짧게.

## 6. 작업 중단과 인수인계

사용자가 "여기까지만", "마무리"라고 하면:
1. 모든 세션에(ListAgents 후) "지금 하던 작업까지만 마무리하고 중단, 새 작업 금지, 멈추면 한 줄 보고(끝낸 것 / 커밋 요청 상태 / 미커밋 파일 / 다음 할 일)".
2. 이 사이에 온 새 제안(수정안 등)은 시작시키지 말고 진행현황 "재개 때 사용자 결정"에 적는다.
3. 다 모이면 사용자에게 표로 정리(원격 HEAD, 마지막 CI, 미커밋 목록, 재개 순서).
4. 인수인계 지시: 각 세션에 `/ecc:save-session`, short-id는 역할 이름(같은 날 두 번째면 `-2`), 넣을 내용을 세션별로 구체적으로. pm도 자기 것을 저장한다.
5. 재개 안내: `/ecc:resume-session ~/.claude/session-data/<날짜>-<역할>-session.tmp`처럼 **경로를 지정**해야 다른 역할 파일을 읽지 않는다.

## 6-1. 세션 띄우기·멈추기·교대 (백그라운드 세션)

역할 세션은 `.claude/skills/pm-ops/scripts/session.ps1`로 다룬다(PowerShell). 역할 정의는 `.claude/agents/<역할>.md`.
- `list` / `health`(대화 크기·교대 권장) / `start <역할> "<지시>"` / `stop <역할>` / `prep <역할>` / `rotate <역할> <경로|none>` / `adopt <역할> <세션ID>` / `pm-cmd`
- **보고를 받으면 그 세션을 바로 `stop`한다.** 멈춘 세션은 메모리 0이고 대화는 남는다. 상주는 `WY-pm`뿐.
- `start`는 늘 지시와 함께. 지시 없이 이어 띄우면 대화가 기록되지 않은 빈 사본이 생겨 다음에 "source session not found"로 실패한다(스크립트가 대화 기록 없는 항목은 역할 파일로 새로 띄움).
- **멈춘 세션은 그동안 온 회신을 못 받는다.** 다시 띄울 때 지시에 "멈춰 있는 동안 끝난 일"(커밋 해시, 병합, 결정)을 넣는다. `docs/진행현황.md`의 "역할별 다음 할 일"을 지시·완료 때마다 갱신한다.
- **메모리는 세션을 띄운 뒤 잰다.** 세션이 뜰 때 순간 약 700MB를 쓴다. 무거운 작업 지시는 띄운 상태에서 1GB 이상일 때. 동시에 띄우는 세션은 2~3개까지.
- 교대: `health`로 5MB 이상이거나 큰 작업·단계가 끝났으면 `prep` → 회신(경로 또는 진행 중 없음) → `rotate` → 새 세션 시작 회신 → 끝난 일 전달. 작업 경계에 맞추면 인수인계 없이(`none`) 교대한다.
- `WY-pm` 교대: 자기 진행 중인 것만 `/ecc:save-session`(short-id `WY-pm`) → `pm-cmd` 출력 한 줄을 사용자에게 → 사용자가 실행하고 이전 창을 닫음.
- 백그라운드 세션의 권한 확인 창은 사용자가 승인할 수 없다. 지시에 "권한 확인이 필요한 동작은 하지 말고 [차단]"을 넣고(역할 파일에도 있음), 대시보드의 승인 대기(노랑 삼각형)는 진짜 승인 대기다. 입력 대기(초록 점)는 일을 마치고 쉬는 상태.
- VS Code Reload Window를 하면 패널 세션 이름이 풀린다. 백그라운드 세션은 영향 없다.

## 7. 단계 마무리 체크 (P1 끝 등)

- 남은 WBS와 qa 항목, 개정 대기 목록 확인 → WY-planner·WY-design 일괄 개정 지시
- PR(feature/P<n> → main) merge commit 병합은 WY-commit, 사용자 승인
- 병합 직전 WY-browser로 운영 변수 이름 확인, 병합 직후 WY-qa로 운영 확인(진행현황 "다음 작업"의 병합 직후 항목)
- 새 단계 브랜치 생성과 배정
