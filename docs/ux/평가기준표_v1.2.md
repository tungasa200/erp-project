## 9. 모바일 평가 절

### 9-1. 에뮬레이션 설정 (반드시 이 순서)
뷰포트만 줄이면 `(hover: hover) and (pointer: fine)` 규칙이 그대로 살아 있어 **데스크톱 hover 화면을 모바일로 착각**한다(앱 CSS에 이 조건이 60곳, `pointer: coarse` 3곳). 그래서 기기 에뮬레이션을 쓴다.
1. `agent-browser --session <이름> set device "iPhone 14"` (390×844, 터치, DPR 3, 모바일 UA). 이름이 없다고 나오면 `set device` 목록에서 390 폭 기기를 고르고 보고서에 적는다. 기기 에뮬레이션이 안 되면 `set viewport 390 844`로 하고 그 보고서의 hover·pointer 관련 판단은 모두 "미측정(에뮬레이션 한계)"으로 적는다.
2. `reload` 뒤 한 번 확인: `eval "matchMedia('(hover: none)').matches + ' ' + matchMedia('(hover: hover) and (pointer: fine)').matches + ' ' + innerWidth + 'x' + innerHeight"` → `true false 390x844`이어야 한다. 결과를 보고서 머리에 적는다.
   - 리드가 2026-10-13에 잰 값(agent-browser, iPhone 14): `hover: none` = true, `pointer: coarse` = **false**, `navigator.maxTouchPoints` = 0, DPR 3. 즉 hover 규칙(60곳)은 꺼져 모바일처럼 보이지만, **`(pointer: coarse)` 규칙 3곳은 적용되지 않는다**. 이 3곳(`grep -rn "pointer: coarse" frontend/src`)이 걸린 요소는 소스를 읽어 판단하고 "에뮬레이션 근사"로 적는다. 터치 이벤트(길게 누르기·끌기)도 실제 터치로 흉내 낼 수 없다.
3. 360 확인: `set viewport 360 780` 뒤 2번 식으로 다시 확인(리드 측정: `hover: none` 유지).
4. **키보드가 올라온 상태 흉내**: 입력에 포커스를 둔 채 `set viewport 390 500`(키보드 약 340px). 앱에 `(max-width: 767px) and (max-height: 560px)` 규칙과 `visualViewport` 처리(QuickSheet)가 있으므로, 이 높이에서 입력 칸·저장 버튼·시트가 보이는지 본다. 실제 iOS 키보드(레이아웃 뷰포트는 그대로이고 visual viewport만 줄어듦)와 다르므로 판단은 "에뮬레이션 근사"로 표시하고, 가려지는지의 최종 확인은 실기기 필요로 넘긴다.
5. 끝나면 `set viewport`를 되돌릴 필요 없이 `close`.

### 9-2. 모바일 판단 기준 (축 7을 나눔, 다른 축과 함께 각 화면에서 본다)
| 항목 | 판단 기준 | 측정 방법 |
|---|---|---|
| M1 가로 넘침 | 390·360에서 페이지가 옆으로 밀리지 않는다. 표·코드·긴 낱말은 자기 상자 안에서 감싸거나 스스로 스크롤하고, 스크롤 단서가 있다 | `eval "document.documentElement.scrollWidth - innerWidth"`(0이어야 함), 넘치는 요소 찾기: `[...document.querySelectorAll('body *')].filter(e=>e.getBoundingClientRect().right>innerWidth+1)` 상위 몇 개 |
| M2 누르는 영역 | 44×44 CSS px(기준표), 최소 24×24(WCAG 2.5.8). 캘린더 칸 예외 24px(D-76) | v1과 같이 max(보이는 상자, ::before·::after 상자). 하단 탭·시트 버튼·목록 행의 체크·더보기(⋯)·닫기(×)·칩 삭제는 반드시 잰다 |
| M3 엄지 영역 | 하루 여러 번 쓰는 주 동작(빠른 기록 +, 저장, 하루 마감, 완료 체크)은 화면 아래 절반(390×844에서 y ≥ 422)에 있거나 아래쪽에서 닿는 길이 있다. 파괴적 동작은 주 버튼과 붙어 있지 않다(8px 이상 띄움) | 요소 중심 y 좌표를 잰다. 위쪽 1/3(y < 280)에만 있으면 지적 |
| M4 하단 시트·모달 | 390에서 대화창은 하단 시트 또는 전체 화면이고, 주 버튼은 시트 아래쪽에 고정되어 스크롤 없이 보인다. 닫기 길이 둘(× 또는 바깥 누르기/끌어내리기 + 뒤로) 이상이고, 시트 높이가 내용에 맞는다. 시트 뒤 본문이 함께 스크롤되지 않는다 | 열고 스냅숏·좌표. 시트 안 스크롤 뒤 `document.scrollingElement.scrollTop` 변화 확인 |
| M5 키보드 가림 | 입력 중인 칸과 그 칸의 저장 버튼이 키보드 위에 보인다(9-1 4번 근사). `enterKeyHint`·`inputmode`·`autocomplete`·`type`(email·tel·number)이 칸 뜻과 맞다. 입력 글자 16px 이상(767px 이하, iOS 확대 방지) | 9-1 4번 + 계산된 `font-size`, 속성은 스냅숏·`eval`로 확인 |
| M6 안전 영역 | `viewport-fit=cover`이므로 하단 탭·고정 버튼·토스트·타이머 띠·시트 아래 여백에 `env(safe-area-inset-*)`가 들어간다 | 소스 grep(`safe-area`)과 계산된 padding. 실제 홈 인디케이터 겹침은 실기기 필요 |
| M7 고정 요소 쌓임 | 하단 탭 + 타이머 띠 + 토스트 + 오프라인 띠 + 설치 안내가 동시에 떠도 본문 마지막 줄과 주 버튼이 가리지 않는다. 화면 아래 고정 높이 합계 ≤ 화면 높이의 25%(390×844에서 약 211px) | 고정 요소 높이 합계를 잼, 본문 마지막 요소가 스크롤 끝에서 보이는지 |
| M8 hover 의존 | 터치 에뮬레이션에서 hover로만 보이던 동작(행 오른쪽 버튼, 툴팁 속 정보)이 보이거나 다른 길(길게 누르기·⋯ 메뉴)이 있다 | 9-1 기기 에뮬레이션 상태에서 스냅숏에 그 버튼이 있는지 |
| M9 직접 조작 | 끌기(캘린더 이동, 시트 끌어내리기)와 세로 스크롤이 충돌하지 않는다. 길게 누르기에 대안 길이 있다 | 소스 읽기(`touch-action`, pointer 처리) + 에뮬레이션 관찰. 손맛(속도·관성)은 실기기 필요 |
| M10 뒤로 가기·주소 | 시트·모달·팔레트를 연 뒤 브라우저 뒤로 가기가 창만 닫는지, 화면을 떠나는지. 하단 탭에서 고른 화면이 새로고침 뒤 유지되는지 | `agent-browser back` 뒤 URL·스냅숏 |
| M11 정보 밀도 | 390 첫 화면(스크롤 전 844px)에 그 화면의 1순위 정보와 주 동작이 들어온다. 위쪽 고정 크롬(머리·탭·필터) 높이 ≤ 화면 높이의 30%(약 253px) | 스크린숏 1장 + 크롬 높이 합 |
| M12 PWA 설치 상태 | 독립 실행(`display: standalone`)에서는 주소창·뒤로 버튼이 없으므로 앱 안에 되돌아갈 길이 있다. 설치 안내(MOB-02)가 설치된 상태에서 다시 뜨지 않는다. `theme-color`가 머리 색과 맞다 | `set media`로는 standalone을 흉내 못 낸다 → 소스 읽기(`display-mode: standalone` 처리) + "실기기 필요" |
| M13 움직임 | 시트·토스트 진입 180ms 이하, `prefers-reduced-motion`에서 꺼짐(D-212 X-12) | `set media light reduced-motion` 뒤 계산된 transition |

- 오프라인(v1 축 4)은 모바일에서 더 자주 일어난다. 자기 영역 주 화면 1개에서 `set offline on`으로 띠 위치·입력 보존을 본다(`set offline off` 잊지 말 것).
- OS 다크 모드(`set media dark`)는 리드만 1회.

### 9-3. 비교 기준(익숙한 모바일 패턴)
Todoist·Things 모바일의 하단 + 빠른 추가(시트 한 장, 키보드와 함께 열림, 저장은 키보드 위 버튼), Google Calendar 모바일의 하단 시트 일정 상세와 FAB, Linear 모바일의 하단 탭 4~5개 + 더보기, iOS·Android 시스템 하단 시트(손잡이, 끌어내려 닫기). 근거로 쓸 때 제품명과 어떤 동작인지 적는다.

### 9-4. 화면마다 순서
1. 390 기기 에뮬레이션(9-1)에서 접근성 스냅숏 → 축 1~8 + M1~M13 → 필요한 화면만 스크린숏(개인 정보 가림, D-206).
2. 같은 화면을 360으로 줄여 M1·M2·M11만 다시 본다.
3. 입력이 있는 화면은 9-1 4번(키보드 근사)으로 M5.
4. 지난 평가의 모바일 관련 지적(통합 v1.1의 390 항목, 재평가 확인 문서)이 이 화면에 있으면 지금 상태를 재확인한다.

### 9-5. 측정 기록 형식
지적의 "증거"에 수치를 적는다. 예: `scrollWidth−innerWidth = 38`, `[완료] 체크 32×32(::after 없음)`, `[저장] 중심 y=268 / 844`, `고정 하단 합계 56(탭)+48(타이머)=104`. 재지 못한 것은 "미측정(이유)".

### 9-6. 스킬 쓰는 순서 (D-200·D-211)
1. `impeccable` — 화면마다 critique(위계·인지 부하)와 audit(접근성·반응형). 주 틀.
2. `frontend-design` — 축 1·2 위계·방향 대안이 필요한 지적에만(모바일 첫 화면 배치, 하단 시트 구성).
3. `emil-design-eng` — 이름으로 불러 시트·토스트·끌기·전환 모션(M9·M13).
4. `web-design-guidelines`(고정 사본) — 마지막에 자기 영역 소스 파일에 대해 축 5·6 점검(터치 영역, `touch-action`, `inputmode`, safe-area, 포커스). 
- 같은 지적이 두 스킬에서 나오면 한쪽만 쓰고 "주 근거 / 보조" 출처를 적는다.

### 9-7. 보고서 끝 목록
v1의 4개(시험 데이터, 권한 필요, 실기기 필요, WY-design 판단)에 더해 **"에뮬레이션 근사 목록"**(키보드 근사·standalone 등 브라우저로 흉내만 낸 판단)을 둔다. 실기기 필요 목록은 사용자가 진행 중인 실기기 테스트와 겹치는지 알 수 있게 화면 ID·확인할 동작·기대 결과를 한 줄로 적는다.

### 9-8. 일정과 보고
- 보조 세션은 끝나면 리드 `WY-ux`에 SendMessage `[완료]` 경로·요약(10줄 안팎). WY-pm에는 보내지 않는다. 막히면 리드에게, 리드가 응답 없으면 WY-pm에 `[차단]`.
- 시작 전과 브라우저 띄우기 전 여유 메모리 확인(500MB 미만이면 멈추고 WY-pm에 `[차단]`). 브라우저는 `agent-browser --session <자기 이름>` 한 줄 명령만, 첫 명령은 출력을 파일로 돌린다. 끝나면 `close`.
- 권한 확인 창이 뜰 동작은 하지 않고 "권한 필요 목록"에 적는다.
