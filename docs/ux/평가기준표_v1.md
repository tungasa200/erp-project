# 디자인 평가 기준표 v1 (2026-10-12, WY-ux)

WY-ux·WY-ux2·WY-ux3는 이 기준만 쓴다. 기준에 없는 판단이 필요하면 보고서에 "기준 밖" 표시를 하고 근거를 적는다(리드가 합칠 때 정리).

## 0. 기준 문서
- 의도: 화면정의서 v2.1(`docs/화면정의서_v2.1.docx`) 2장(디자인 방향·색·상태 표현·반응형·공통 상호작용·말투)과 3장(화면별), 토큰 `frontend/src/theme/tokens.css`, AI 티 필터 `docs/ux/AI티_필터_v0.md`.
- 지적마다 둘 중 하나를 고른다. **구현 차이**: 구현이 화면정의서·토큰과 다르다(고칠 곳은 코드). **의도 문제**: 화면정의서대로인데 사용자 경험이 나쁘다(고칠 곳은 화면정의서, 결정은 WY-design·사용자).
- 다크 테마는 화면정의서에서 "준비 중"이라 이번 범위가 아니다. 대신 배경 4종(쿨 그레이 기본·웜 베이지·세이지·화이트)과 키 컬러 변경을 "테마"로 본다. OS가 다크 모드일 때 앱이 어떻게 보이는지만 한 번 확인한다(리드).

## 1. 심각도
| 심각도 | 정의 | 예 |
|---|---|---|
| 높음 | 핵심 흐름(빠른 기록 → 하루 마감 → 일지 내보내기)을 막거나, 데이터 실수(잘못 저장·삭제·덮어쓰기, 못 되돌림)를 일으킨다. WCAG 2.2 AA 위반 중 기능을 쓸 수 없게 하는 것 | 저장 버튼이 키보드로 닿지 않음, 모바일에서 주 버튼이 가려 누를 수 없음, 대비 3:1 미만인 본문 |
| 중간 | 매번 느리게 하거나 헷갈리게 한다. 기능은 되지만 반복 사용에서 비용이 쌓인다. 기능을 막지 않는 AA 위반 | 클릭 1~2번 더 필요, 같은 일을 하는 두 길이 다르게 동작, 포커스 표시 약함, 누르는 영역 44px 미만 |
| 낮음 | 다듬기. 일관성·여백·문구·토큰 밖 값 | 반 픽셀 글자 크기, 모서리 값 제각각 |
| 제안(취향) | 근거가 취향뿐 | "이 색이 더 낫다" |

- 심각도는 "빈도 × 영향"으로 정한다. 하루 여러 번 지나는 화면(홈·빠른 기록·하루 마감)은 같은 문제라도 한 단계 높게 볼 수 있다. 올렸으면 사유를 적는다.

## 2. 평가 축과 판단 기준 (각 화면에서 이 순서)
| 축 | 판단 기준 | 측정 방법 |
|---|---|---|
| 1 시각 위계 | 3초 안에 주 작업과 가장 중요한 정보가 보이는가. 크기·굵기·색·여백·위치가 중요도 순서와 맞는가. 주 버튼(accent 채움)은 화면당 하나 | 스크린숏을 흐리게 봤을 때 1순위 1개·2순위 2~3개, 화면의 accent 채움 버튼 수 셈 |
| 2 정보 구조·흐름 | 핵심 흐름의 단계·클릭·입력 수, 막다른 곳, 되돌아가기, 같은 일을 하는 두 길 | 실제로 눌러 클릭·키 입력 수를 셈. 비교 기준(Todoist 빠른 추가 1단계, Linear Cmd+K 등)과 나란히 |
| 3 생산성 도구 특성 | 키보드만으로 되는가(단축키, Enter·Esc, 포커스 순서), 입력 속도, 정보 밀도, 기본값의 질, 중단 뒤 이어하기, 실행 취소 | Tab만으로 주 동작까지 몇 번, Esc·Enter 동작, 되돌리기 토스트 유무, 새로고침 뒤 입력 유지 |
| 4 상태 설계 | 빈 상태·로딩·오류·오프라인·대량 데이터(한 달 300개 일정, 긴 제목 80자)·첫 사용 | 빈 계정, 긴 제목 입력, 네트워크 끊김(agent-browser `set offline`) |
| 5 일관성 | 같은 의미는 같은 모양·말·위치. 토큰 밖 값 | 계산된 스타일 집계(글자 크기·모서리·그림자 종류 수), 소스 grep |
| 6 접근성 | WCAG 2.2 AA: 대비(본문 4.5:1, 큰 글자·컨트롤 3:1), 누르는 영역 44px(캘린더 예외 D-76은 24px), 포커스 표시, 낭독기 이름, 움직임 줄이기 | 대비는 계산값만 씀. 누르는 영역은 max(보이는 상자, ::before·::after 상자). 이름은 접근성 스냅숏 |
| 7 웹/모바일 | 360·390·768·1280px, 테마, 터치(엄지 영역, 길게 누르기, 스크롤과 끌기 충돌), PWA 독립 실행 | 폭별 스냅숏·스크린숏. 터치·PWA는 "실기기 필요"로 모음 |
| 8 AI 티 | `AI티_필터_v0.md` AIT 항목. 기계 판정 → `impeccable detect` 대조 → 눈 판정(AIT-06·07·11·20·27) | 토큰 자체가 패턴과 겹치면 지적하지 않고 "WY-design 판단 목록"에 올림 |

- "재지 않은 것은 단정하지 않는다." 측정 못 한 것은 "미측정"으로 적는다.
- 취향과 원칙 구분: 근거(닐슨 휴리스틱 번호, WCAG 조항, 측정값, 익숙한 패턴의 제품명)가 없으면 "제안(취향)".

## 5. 계정과 상태 바꾸는 동작
- 대상: 운영 https://wy-worklog.com. 계정은 `C:\projects\worklog-secret\secret.txt`에서 읽고 값은 어디에도 옮기지 않는다(보고서·메시지·메모리·명령 기록 파일 금지).
- TEST_EMAIL 계정은 사용자 본인 계정이다. **쓰지 않는다**(필요하면 읽기만, 이번 평가에는 쓰지 않음).
- 세션마다 계정을 따로 써서 상태가 섞이지 않게 한다. 비밀번호가 맞지 않으면 같은 계정의 `_ALT` 값을 한 번 시도하고, 그래도 안 되면 그 계정은 건너뛰고 보고서에 적는다(비밀번호 재설정 메일 발송 금지).

| 세션 | 계정 | 상태를 바꿔도 되는 동작 |
|---|---|---|
| WY-ux | TEST_B | 타이머 시작·정지(COM-06), 빠른 기록·홈 기록 만들기, 설정 › 일반 단축키 켜고 끄기(확인 뒤 원래대로) |
| WY-ux2 | TEST_A | 기록·업무 만들기·고치기·완료·보관, 하루 마감, 일지 초안·확정·확정 해제, 내보내기 파일 받기 |
| WY-ux3 | TEST_L | 일정 만들기·끌기·반복, 설정 › 테마·알림·일반·프로젝트·태그 바꾸기(끝나면 원래 값으로), 알림 읽음 처리 |

- 금지: 실제 메일 발송(내보내기 전 이메일 인증 코드 요청, 비밀번호 찾기, 가입, 인증 메일 재발송), 가입, 탈퇴, 비밀번호·이메일 변경, 웹 푸시 구독 허용, 다른 세션 계정으로 로그인. 메일 화면(MAIL-01·02)은 화면정의서·목업과 메일 템플릿 소스로만 본다.
- 시험 데이터는 제목을 `[UX-평가]`로 시작하게 만들고, 만든 것을 보고서 "시험 데이터 목록"에 남긴다(지우지 않음, REL-07 뒤 정리, D-204).
- 한 달 300개 일정 같은 대량 데이터는 운영에 만들지 않는다. 대량 상태는 긴 제목(80자)·한 칸 12개 겹침 정도만 만들고, 그 이상은 "미측정(대량 데이터)"으로 적는다.

## 6. 도구와 순서
1. 메모리 확인: PowerShell `(Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory` (KB). 500MB(512000) 미만이면 시작하지 않고 `WY-pm`에 [차단].
2. 브라우저: CLI `agent-browser --session <자기 세션 이름> ...`만 쓴다. MCP 브라우저 도구는 쓰지 않는다. `WY-browser`의 CDP 9222에 붙지 않는다. 끝나면 `agent-browser --session <이름> close`.
3. 화면마다: 접근성 스냅숏 → 축 1~8 순서 → 필요한 화면만 스크린숏(개인 정보 칸, 특히 계정 메일은 가리고 찍거나 그 칸을 잘라냄. D-206).
4. AI 티: 필터 §5 순서. 소스 grep·계산된 스타일 집계 → `impeccable detect --json <파일>` → 눈 판정.
5. 스킬: `impeccable`(critique·audit)을 쓴다. D-200 스킬 3개(frontend-design·emil-design-eng·web-design-guidelines)는 아직 설치 전이다. 그 스킬이 필요했던 지적에는 `[스킬 대기: 이름]`을 붙인다(위계·방향 제안 → frontend-design, 모션·인터랙션 → emil-design-eng, 축 5·6 마지막 점검 → web-design-guidelines). impeccable 결과와 자기 판단이 겹치면 한쪽만 쓰고 출처를 적는다.
6. 권한 확인 창이 뜰 동작은 하지 않는다. 건너뛴 것은 보고서 "권한 필요 목록"에 적고 계속한다.
7. 코드·화면정의서·목업은 고치지 않는다. 커밋 요청도 보내지 않는다(아침에 WY-pm이 묶음).

## 7. ID 규칙과 보고 형식
- 지적 ID: `UX-{영역}-{번호}`. 영역 = 화면 ID의 영역(COM·HOME·MOB·SYS·REC·TASK·LOG·STAT·FORM·CAL·SET·AUTH·ONB·MAIL). 번호는 세션별 대역으로 겹치지 않게 한다: WY-ux 01~39, WY-ux2 40~69, WY-ux3 70~99. 예: `UX-LOG-41`, `UX-CAL-72`. 공용 요소 지적은 `[공용]`을 붙인다.
- 보고서 경로: `docs/ux/디자인평가_{세션}_v1.md`(예: `디자인평가_WY-ux2_v1.md`). 스크린숏은 `docs/ux/evidence/{세션}/`(커밋 안 됨, D-207). 이름은 `{지적 ID 또는 화면 ID}-{폭}.png`.
- 보고서 첫머리 요약: 가장 큰 문제 5개(영향 순), 잘된 점 3개(유지할 것).
- 지적 하나마다 아래 칸:

```
### UX-LOG-41 (제목 한 줄)
- 화면: SCR-LOG-03 · 폭/테마: 390 기본 · 축: 2 · 심각도: 중간 · 구분: 구현 차이|의도 문제
- 문제: …
- 영향: (사용자에게 미치는 영향)
- 제안: …
- 근거: (휴리스틱·WCAG 조항·측정값·익숙한 패턴)
- 증거: docs/ux/evidence/WY-ux2/UX-LOG-41-390.png, 스냅숏 요약, 측정값
```

- 보고서 끝에 별도 목록 4개: "시험 데이터 목록", "권한 필요 목록", "실기기 필요 목록"(터치·PWA·iOS 입력 확대·키보드가 올라올 때 배치 등), "WY-design 판단 목록"(토큰 자체가 패턴과 겹치는 것).
- 끝나면 `WY-ux`(리드)에게 SendMessage로 `[완료]` 경로와 요약을 보낸다. WY-pm에는 보내지 않는다(리드가 합쳐 보냄). 막히면 리드에게 먼저, 리드가 응답 없으면 WY-pm에 [차단].
