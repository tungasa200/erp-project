## 요약

### 가장 큰 문제 5개 (영향 순)
1. **UX-COM-01 Esc 한 번에 빠른 입력 글이 사라지고 되돌릴 수 없다.** 홈 입력칸은 Esc로 글을 비우고 Ctrl+Z로도 돌아오지 않는다. 같은 입력이 모바일 시트에서는 Esc를 눌러도 글을 남긴다. 하루에 가장 많이 쓰는 입력에서 일어나는 데이터 손실이다.
2. **UX-COM-02 기록 직후 Ctrl+Z가 듣지 않는다.** 저장한 뒤에도 포커스가 입력칸에 남아 있어서 Ctrl+Z가 브라우저 기본 입력 되돌리기로 먹힌다. 결과적으로 가장 흔한 되돌리기 상황에서 단축키가 동작하지 않는다.
3. **UX-COM-03 명령 팔레트에서 검색어가 기존 업무와 맞아도 첫 항목이 "업무로 추가"다.** 찾으려고 Enter를 누르면 같은 이름의 업무가 새로 생긴다.
4. **UX-HOME-01 홈의 위계가 주 작업(빠른 기록)과 맞지 않다.** 가장 큰 글자는 정보가 없는 인사말이다. 가장 눈에 띄는 요소는 키 컬러로 채운 "남은 업무" 타일이다. 빠른 입력은 오른쪽 위 흰 알약 안에 있고, 그 안내 문구(대비 3.2:1)가 보이는 라벨의 전부다. 키 컬러로 채운 요소도 화면당 3개(모바일은 4개)다.
5. **UX-COM-10 입력 글자 크기 16px 미만 21곳(홈 빠른 입력 15px 포함).** iOS Safari는 이런 칸에 포커스가 가면 화면을 확대한다. 모바일 시트(16px)만 피해 간다. 실기기 확인이 필요하다.

### 잘된 점 3개 (유지할 것)
1. **빠른 기록 1단계.** `14-15 #견적 ~내일` 한 줄을 Enter 한 번에 업무와 일정으로 만들고, 되돌리기 토스트를 띄우고, 포커스를 입력칸에 남기고, 홈 카드 4곳을 바로 갱신한다. 해석 칩(시간·태그·우선순위·마감)이 실제 날짜로 보이고, 입력칸 아래 "일정과 업무가 함께 만들어져요"가 결과를 미리 알려 준다. Todoist 빠른 추가와 같은 수준이다.
2. **모바일 빠른 기록 시트.** 입력 16px, 자동 포커스, Esc·닫기 때 초안 유지, 오프라인 때도 초안을 남기고 입력만 끈다. 시트 닫힘 뒤 포커스가 + 버튼으로 돌아간다.
3. **모션이 절제돼 있고 AI 티가 적다.** 애니메이션 6개가 모두 상태 변화·로딩용이다. 움직임 줄이기는 6파일에서 대응한다. 그라데이션 글자·글래스·이탤릭 제목·대문자 라벨·굵은 한쪽 띠가 모두 0건이다. 키보드 기본기도 갖췄다: N 단축키, Ctrl+K, 팔레트를 닫으면 원래 자리로 포커스 복귀, 키 컬러 포커스 링, 태블릿 아이콘 레일의 aria-label·title.

## 지적

### UX-COM-01 Esc가 빠른 입력 글을 지우고 되돌릴 수 없음
- 화면: SCR-COM-02 · 폭/테마: 1280 기본 · 축: 3 · 심각도: 중간 · 구분: 의도 문제(화면정의서 "Esc로 입력 비우기") + 구현 차이(SCR-MOB-01과 다르게 동작)
- 문제: 홈 빠른 입력에 글을 쓰고 Esc를 누르면 글이 사라진다. Ctrl+Z로도 돌아오지 않는다(측정: Esc 직후 Ctrl+Z, value ""). 같은 문법을 쓰는 모바일 시트는 Esc를 눌러도 글을 남긴다.
- 영향: 팝오버를 닫으려거나 칩 메뉴를 닫으려고 습관처럼 누른 Esc 한 번에 긴 입력이 사라진다. 같은 입력이 화면마다 다르게 동작해서 학습한 기대도 깨진다.
- 제안: Esc는 "포커스 빼기"로만 쓰고 글은 남긴다(시트와 같게). 비우기가 꼭 필요하면 Esc 두 번 또는 입력칸의 × 버튼으로 하고, 비운 글은 Ctrl+Z로 복원되게 한다.
- 근거: 닐슨 휴리스틱 3(사용자 통제·자유)·5(오류 예방)·4(일관성). Linear·Todoist 빠른 추가는 Esc로 창만 닫고 초안을 남긴다.
- 증거: 브라우저 측정(Esc 뒤 value "", Ctrl+Z 뒤 ""), 시트에서는 Esc 뒤 다시 열었을 때 초안 유지.

### UX-COM-02 기록 직후 Ctrl+Z가 앱 되돌리기로 동작하지 않음
- 화면: SCR-COM-02·COM-04 · 1280 · 축: 3 · 심각도: 중간 · 구분: 구현 차이(2.5 단축키 "Ctrl+Z 되돌리기")
- 문제: 빠른 기록을 Enter로 저장하면 포커스가 입력칸에 남는다. 이 상태에서 Ctrl+Z를 누르면 토스트는 그대로 있고 업무도 남는다(측정: "날짜 없는 업무" 4→5개 그대로).
- 영향: 앱 되돌리기가 가장 필요한 순간(방금 잘못 넣은 기록)에 단축키가 듣지 않는다. 결국 마우스로 토스트를 눌러야 한다.
- 제안: 입력칸이 비어 있을 때의 Ctrl+Z는 앱 되돌리기로 넘긴다. 또는 토스트가 떠 있는 동안 입력칸의 Ctrl+Z를 토스트 되돌리기로 보낸다.
- 근거: 휴리스틱 3. Gmail·Todoist는 토스트가 떠 있는 동안 Ctrl+Z(또는 z)로 방금 동작을 되돌린다.
- 증거: 측정 기록(시험 업무 "[UX-평가] 되돌리기 시험"이 남음).

### UX-COM-03 팔레트 검색이 기존 업무와 맞아도 "업무로 추가"가 첫 선택
- 화면: SCR-COM-03 · 1280 · 축: 2·3 · 심각도: 중간 · 구분: 구현 차이(화면정의서: "어떤 명령과도 맞지 않으면" 첫 항목으로 추가 제안)
- 문제: "견적"을 치면 첫 항목(선택됨)이 "'견적'을 업무로 추가"이고, 기존 업무 "[UX-평가] 견적서 검토"는 두 번째다.
- 영향: 업무를 찾으려고 친 사용자가 Enter를 누르면 같은 이름의 업무가 하나 더 생긴다. 토스트로 되돌릴 수는 있지만 매번 확인해야 한다.
- 제안: 결과가 있으면 결과를 먼저 두고 "업무로 추가"는 맨 아래로 보낸다. 결과가 없을 때만 첫 항목으로 둔다.
- 근거: 화면정의서 SCR-COM-03 상태·예외. Linear·Raycast는 검색 결과를 먼저 두고 "새로 만들기"를 맨 아래에 둔다.
- 증거: 접근성 스냅숏(option "'견적'을 업무로 추가" [selected], 이어서 group "업무").

### UX-COM-04 팔레트 구성이 화면정의서보다 적고 이름표가 영어
- 화면: SCR-COM-03 · 1280 · 축: 3·6 · 심각도: 낮음 · 구분: 구현 차이
- 문제: 입력 전 목록에 "최근 사용"이 없다. 동작 그룹에 "일정 추가"가 없다(업무 추가·하루 마감만 있음). 목록의 낭독기 이름이 cmdk 기본값 "Suggestions"다.
- 영향: 일정을 키보드로 만드는 길이 팔레트에 없다. 낭독기 사용자는 한국어 화면에서 영어 이름을 듣는다.
- 제안: 화면정의서 ②④대로 채우고, listbox 이름을 "결과"로 바꾼다.
- 근거: SCR-COM-03 구성 요소 ②④. WCAG 3.1.2(부분 언어)는 참고만 한다.
- 증거: 스냅숏(listbox "Suggestions"), `COM-03-palette-1280.png`.

### UX-COM-05 타이머 시작 창에서 업무를 고르면 포커스가 사라짐
- 화면: SCR-COM-06 ⑦ · 1280 · 축: 3·6 · 심각도: 중간 · 구분: 구현 차이
- 문제: "연결 업무"에서 ↓·Enter로 업무를 고르면 콤보박스가 "업무 링크 + 해제"로 바뀌고, 포커스가 문서 맨 위(루트 div)로 빠진다. 이어서 누른 Enter는 아무 일도 하지 않는다. 고른 업무는 밑줄 링크로 보여서 누르면 창을 떠날 것처럼 보인다. "할 일" 칸은 "(비우면 업무 제목)" 안내가 업무를 고른 뒤에야 나타나고, "새 업무" 버튼은 비활성처럼 흐리다.
- 영향: 키보드만 쓰는 사람은 업무를 고른 뒤 Tab을 처음부터 다시 눌러야 시작할 수 있다. 칸 두 개의 관계(연결 업무 vs 할 일)도 처음 보면 헷갈린다.
- 제안: 고른 뒤 포커스를 [시작] 또는 "할 일" 칸으로 옮긴다. 고른 업무는 링크가 아닌 칩으로 보이고, "할 일" 안내는 처음부터 보인다.
- 근거: WCAG 2.4.3(포커스 순서), 휴리스틱 6(기억보다 알아보기). Toggl은 설명 한 칸 + 프로젝트 선택으로 시작한다.
- 증거: 측정(activeElement가 루트 div), `COM-06-start-1280.png`, `COM-06-running-1280.png`.

### UX-COM-06 없는 프로젝트를 쓰면 Enter가 막히는데, 아래 안내는 "만들어져요"
- 화면: SCR-COM-02 · 1280 · 축: 2·3 · 심각도: 중간 · 구분: 의도 문제(화면정의서 "새 프로젝트 만들기 칩으로 확인 후 생성")
- 문제: `@영업`(없는 프로젝트)이 들어간 줄에서 Enter를 누르면 status로 "'영업' 프로젝트가 없어요. 아래 칩을 눌러 먼저 만들어 주세요"가 뜨고 저장되지 않는다. 그런데 입력칸 아래 미리보기 문구는 계속 "일정과 업무가 함께 만들어져요"다. 칩은 Tab으로 몇 번 가거나 마우스로 눌러야 한다.
- 영향: 결과 미리보기와 실제 결과가 어긋난다. 새 프로젝트를 쓸 때마다 손을 키보드에서 떼거나 Tab을 여러 번 눌러야 한다.
- 제안: 미리보기 문구를 "새 프로젝트 '영업'을 만들어야 저장돼요"로 바꾼다. Enter 한 번 더(또는 Shift+Enter)로 "만들고 저장"을 하게 한다.
- 근거: 휴리스틱 1(시스템 상태)·7(효율). Todoist는 없는 프로젝트를 쓰면 자동완성에서 "만들기"를 바로 고를 수 있다.
- 증거: 스냅숏(status 문구, 미리보기 문구 동시 표시), `COM-02-chips-1280.png`.

### UX-COM-07 입력하는 동안 홈 전체가 아래로 밀림
- 화면: SCR-COM-02·HOME-01 · 1280·390 · 축: 1·4 · 심각도: 낮음 · 구분: 구현 차이
- 문제: 글자를 치기 시작하면 아래 미리보기 줄이 생겨 요약 타일이 12px 내려간다. 칩이 두 줄이 되면 92px까지 내려간다(측정: 타일 top 115 → 127 → 207).
- 영향: 입력 중에 아래 카드를 보고 있던 시선이 흔들린다. 저장 뒤에는 다시 올라간다.
- 제안: 칩·미리보기를 입력칸 아래 띄운 층(팝오버)으로 두거나, 자리를 미리 잡아 둔다.
- 근거: Core Web Vitals CLS 개념, 휴리스틱 8(미니멀).
- 증거: `COM-02-typing-1280.png`, `COM-02-chips-1280.png`.

### UX-COM-08 해석 결과에 "제목"이 따로 안 보임
- 화면: SCR-COM-02 · 1280 · 축: 2 · 심각도: 제안(취향) · 구분: 의도 문제
- 문제: 칩은 시간·태그·마감을 보여 주지만, 남는 제목이 무엇인지는 원문에서 직접 짐작해야 한다.
- 제안: 입력칸 안에서 해석된 낱말에 색을 입히거나(Todoist 방식), 미리보기 줄에 "제목: …"을 둔다.
- 근거: 익숙한 패턴(Todoist·Things 자연어 강조). 근거가 패턴뿐이라 제안으로 둔다.

### UX-COM-09 빠른 입력의 보이는 라벨이 대비 3.2:1 안내 문구뿐
- 화면: SCR-COM-02 · 전 폭 · 축: 6 · 심각도: 중간 · 구분: 구현 차이(2.2 "보조 텍스트도 4.5:1 이상")
- 문제: 라벨 "빠른 기록"은 화면에서 숨겨져 있고, 안내 문구(#8A8FA3, 흰 바탕 대비 3.2:1 계산값)가 눈에 보이는 유일한 설명이다.
- 영향: 저시력·밝은 환경에서 앱의 가장 중요한 입력칸이 무엇인지 읽기 어렵다.
- 제안: 안내 문구 색을 --color-text-muted(#5E6377, 6.0:1)로 올리거나, 입력칸 왼쪽에 아이콘·보이는 라벨을 둔다.
- 근거: WCAG 1.4.3(텍스트 대비 4.5:1), 화면정의서 2.2.
- 증거: 계산값 3.21(::placeholder rgb(138,143,163) / 흰 바탕).

### UX-COM-10 입력 글자 16px 미만 21곳 — iOS 포커스 확대 (후보 검증)
- 화면: 공용(홈 빠른 입력 15px, 업무 검색 14px, 설정 select 14px, 캘린더 입력 13~15px, 인증 15px 등) · 390 · 축: 7 · 심각도: 중간 · 구분: 구현 차이 · **실기기 필요**
- 문제: 입력·select 규칙 21곳이 13~15px이고, body 기본도 15px이다. viewport meta에 확대 막기가 없고(막는 것은 접근성상 맞지 않음), 16px로 올리는 모바일 규칙도 없다. 모바일 시트만 16px다.
