## ① 뒤로 가기·history — [결정] 쟁점 1 (UX-M-COM-02 + CAL-71)

### 원칙
**휴대폰의 뒤로 가기는 "맨 위에 열린 창 하나를 닫는다".** 창이 없을 때만 화면을 떠난다. 닫을 때 쓰던 글은 남긴다(D-212 Q1과 같다: Esc·바깥 누르기·뒤로 가기가 모두 같은 "닫기"다).

### 범위 (안 B, 추천)
- 대상: **하단 시트와 전체 화면 패널**. 폭과 관계없이 같은 컴포넌트는 같게 동작한다(데스크톱의 같은 창도 브라우저 뒤로 가기로 닫힌다).
  - 빠른 기록 시트(SCR-MOB-01), 기록 추가·수정(SCR-REC-01), 확인 대기 패널(SCR-HOME-02), 하루 마감(SCR-LOG-03), 일정 상세 시트(SCR-CAL-04·07), 통계 직접 선택 시트(SCR-STAT-01), 모바일 더보기 메뉴(SCR-COM-01), 이메일 인증 창(인증 모달)
- 제외: 팝오버(새 일정 팝오버 SCR-CAL-06, 칩 메뉴, "+n" 목록), 명령 팔레트, 문법 도움말, 토스트, 창 안 확인 줄. 작고 바깥 누르기로 닫히며, history를 쌓으면 화면을 떠나려는 뒤로 가기가 여러 번 필요해진다.
- 이미 주소가 있는 패널(업무 상세 `/tasks/{id}`)은 지금 방식(주소 = 상태)을 유지한다. 본보기다.

### 동작 규칙 (공용 훅 하나, WY-frontend)
1. 창을 열 때 **주소를 바꾸지 않고** history 항목 하나를 넣는다(`pushState`, 상태에 창 표식).
2. 뒤로 가기(`popstate`)가 오면 맨 위 창만 닫는다. 글·입력값은 그대로 둔다.
3. 창 안 [×]·Esc·바깥 누르기·[저장]으로 닫으면, 그 창이 넣은 항목이 맨 위일 때만 `history.back()`으로 되돌린다(남은 항목 때문에 다음 뒤로 가기가 헛도는 것을 막는다).
4. 고친 내용이 있는 창(D-212 X-04 dirty): 뒤로 가기는 Esc와 같다. 창을 닫지 않고 창 안 확인 줄("고친 내용이 있어요. 버리고 닫을까요?" [계속 편집]·[버리고 닫기])을 띄우고 항목을 다시 넣는다. 한 번 더 뒤로 가기는 [계속 편집]과 같다.
5. 창 위에 창(전체 화면 패널 안에서 시트)은 한 층에 항목 하나. 뒤로 가기 한 번에 한 층씩 닫힌다. 확인 줄은 층으로 세지 않는다.
6. 창 안 링크로 다른 화면에 가면 창을 닫고 그 이동은 `replace`로 한다(닫힌 창의 항목이 남지 않게).
7. 새로고침 뒤 history 상태에 창 표식이 남아 있으면 `replaceState`로 지운다(열리지 않은 창 때문에 뒤로 가기가 한 번 헛돎을 막는다).
8. 일지 화면의 `useBlocker`(보내지 않은 줄 확인)는 화면을 떠날 때의 확인이라 그대로 둔다. 창이 열려 있으면 창 닫기가 먼저다.

### 확인 방법
- 390 에뮬레이션: 시트 열기 → `back` → 시트만 닫히고 URL 그대로, 글 남음. [×]로 닫은 뒤 `back` → 이전 화면으로 한 번에 감.
- 실기기(REL-07): Android 제스처·iOS 가장자리 스와이프, PWA 독립 실행에서 앱이 꺼지지 않음.

## ③ 390 첫 화면 밀도 — [결정] 쟁점 3 (UX-M-TASK-43·CAL-72·HOME-04)

### 원칙 (기준표 M11을 규칙으로)
1. **390 첫 화면(스크롤 전 844px, 하단 탭 제외 772px)에는 그 화면의 1순위 정보와 주 동작이 들어온다.** 목록 화면의 1순위는 목록 첫 행들이다.
2. **위쪽 크롬(머리·검색·필터·정렬·탭) 합계는 화면 높이의 30%(253px) 이하.** 넘으면 하루 한두 번 바꾸는 컨트롤부터 접는다.
3. **하루 한두 번 바꾸는 컨트롤은 한 줄 버튼 + 하단 시트로 접는다.** 버튼에 지금 적용된 개수를 보인다("필터 2"). 하루 여러 번 쓰는 것(검색, 추가 칸)은 접지 않는다.
4. **같은 정보를 첫 화면에 두 번 보이지 않는다.** 0건인 카드는 접어 한 줄로 두거나 숨긴다(요약 줄에 이미 "0"이 있으면 숨김).
5. **빈 공간이 화면의 20%를 넘게 남으면 다음 우선순위 정보로 채운다.** 다른 화면으로 가야만 보이는 정보가 후보다.

### 적용 (안 A, 추천: 세 곳 한 번에)

## ⑤ 가입 흐름 말투 — [WY-design] 쟁점 4-2: 안 (b)

### 결정
- **D-36의 합니다체는 가입 폼(입력·동의·폼 오류·폼 안내)까지다.** 폼을 내면 나오는 코드 단계는 공용 `CodeStep`의 해요체를 그대로 쓴다.
- 이유
  1. D-36이 사무적 말투를 정한 곳(가입, 처리방침·약관, 국외 이전, 탈퇴)의 공통점은 **약관·동의·권리에 관한 문장**이다. 코드 입력은 그런 문장이 아니고, 같은 코드 입력을 쓰는 `/verify-email`·인증 모달·비밀번호 재설정과 같은 조작 화면이다.
  2. `CodeStep`은 세 곳이 함께 쓰는 컴포넌트다. 가입에서만 합니다체로 바꾸면 문구를 둘로 나눠야 하고, 같은 조작이 화면마다 다른 말이 된다.
  3. 체가 바뀌는 지점이 "폼 → 코드 단계" 한 곳으로 정리된다. 지금 문제는 한 화면 안에서 섞이는 것(배너 합니다 + 안내 하세요 + 오류 해요)이다.
- 그래서 고칠 문구(묶음 M1, WY-frontend)
  - 코드 안내 4곳(`SignupPage.tsx:178`, `VerifyEmailPage.tsx:60`, `EmailVerificationDialog.tsx:105`, `ResetPasswordPage.tsx:89`): "…으로 보낸 6자리 숫자를 입력하세요." → "…으로 보낸 6자리 숫자를 입력해 주세요"(하세요체 없앰, 로그인과 같은 어미).
