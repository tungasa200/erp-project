# 사용자 매뉴얼(PDF) 작업계획 v1

작성 WY-planner, 2026-10-12. 지시 WY-pm(사용자 지시 2026-10-12). 이 문서는 계획만 담는다. 매뉴얼 본문·스크린숏은 아직 만들지 않는다.

## 1. 목표와 범위

- 대상: WY Worklog를 처음 쓰는 사용자. 읽고 나면 "일정·업무·기록이 각각 무엇이고, 하루를 어떤 순서로 쓰는지"를 헷갈리지 않아야 한다.
- 형식: PDF 한 권. 스크린숏과 실제 예시(가상 데이터)를 섞는다. 한글 글꼴 Pretendard.
- 화면 기준: 업무일지 숨김(D-214) 뒤의 화면. 업무일지(SCR-LOG-01·02·04)·내보내기(SCR-LOG-05·06)·회사 양식(SCR-FORM-01·02)은 넣지 않는다. 하루 마감(SCR-LOG-03)은 '일지' 말이 빠진 모양으로 넣는다.
- 스크린숏은 PR #20(feature/records-only)이 운영에 배포된 뒤 운영에서 찍는다.

## 2. 꼭 다룰 것 1 — 헷갈리는 용어

정의는 요구사항정의서 v2.4 1.4 용어 정의와 각 요구사항, 결정기록을 근거로 맞춘다. 매뉴얼에는 아래를 쉬운 말로 풀어 쓰고, 각 용어마다 "무엇 / 언제 쓰나 / 어디서 보나 / 다른 용어와 어떻게 이어지나"를 같은 틀로 쓴다.

| 용어 | 정의(근거) | 매뉴얼에서 짚을 점 |
|---|---|---|
| 업무 | 수행할 일의 단위. 상태·우선순위·마감일·프로젝트·태그·진행률을 가진다 (1.4, TASK-01~05) | 앱의 중심. 일정과 기록은 업무에 붙는다 |
| 할 일 | 별도 항목이 아니라 **업무의 상태** 하나: 할 일 / 진행 중 / 완료 / 보류 (TASK-02) | 가장 헷갈리는 말. "할 일을 만든다"가 아니라 "업무를 만들면 상태가 할 일" |
| 일정 | 캘린더의 시간 구간. 반복할 수 있고 업무와 연결할 수 있다 (1.4, SCH-02·03) | 일정 = "언제 할지"의 계획. 업무 없는 일정(회의 등)도 된다 |
| 계획 블록 | 업무가 연결된 일정(회차). 캘린더 업무 패널에서 업무를 끌어 놓으면 1시간 일정이 생긴다 (SCH-04·07) | 화면에서 '계획'이라 부르는 것의 실체 |
| 업무 기록 | "무엇을 했고 결과가 어떤가". 시간은 선택 (1.4, REC-01) | 일정(계획)과 다르다: 기록 = 실제로 한 것 |
| 확인 대기 | 업무가 연결된 일정이 끝나면 자동으로 생기는 기록 후보. 사용자가 확인해야 기록이 된다. 최근 7일만 홈에 보인다 (1.4, REC-03, D-39·D-100) | 흐름의 핵심 고리: 일정 끝 → 확인 대기 → [확인]/[수정]/[하지 않음] 또는 [모두 했어요] → 기록 |
| 기록 상태 | 확인 대기 / 확정 / 하지 않음. 직접 쓴 기록은 확정 고정 (REC-01, D-98) | 업무 상태(할 일·완료…)와 다른 축임을 표로 대비 |
| 결과 한 줄·칩 | 완료할 때 결과 문구와 칩(완료 / 검토 요청 / 진행 중 n%) (REC-02, SCR-TASK-03) | 업무 완료 = 기록 하나가 남는 순간 |
| 빠른 입력 | 한 줄로 업무·시간·프로젝트·태그·우선순위·마감 입력: `14-16 견적서 작성 @영업 #견적 !높음 ~금` (REC-04, D-106) | 시간을 쓰면 일정까지 생긴다 — 무엇이 생기는지 예시 3개로 |
| 하루 마감 | 확인 대기 처리 → 내일 계획 → [오늘 마감] (LOG-13, D-212 Q2·Q4, D-214 ①) | 화면엔 '일지' 말이 없다. 홈 띠는 하루 마감 시각(기본 18:00) 뒤 |
| 내일 계획(이월) | 하루 마감 때 미완료 업무를 다음 근무일로 넘기는 선택. 업무 자체(상태·마감일)는 바꾸지 않는다 (LOG-14, D-107) | 아래 "확인 필요 ①" — 숨김 뒤 어디서 보이는지 확정해야 씀 |
| 시간 기록 옵션·타이머 | 기본 꺼짐. 켜면 타이머·소요시간·빈 시간 메우기가 보인다 (TIME-03·09·10·11) | 옵션을 켠 화면과 끈 화면이 다르다 — 한 장(章)으로 따로 |
| 보관 | 삭제 대신 보관, 보관함에서 복원. 영구 삭제 없음 (TASK-01·08) | "지웠는데 어디 갔나" 질문에 답 |

용어 관계는 그림 한 장으로 그린다: 업무 ─(연결)→ 일정 ─(끝남)→ 확인 대기 ─(확인)→ 기록 ─(하루 마감)→ 마감한 날 / 내일 계획.

## 3. 꼭 다룰 것 2 — 업무 기록 워크플로우

가상 사용자의 하루 하나를 처음부터 끝까지 따라간다(아래 4장의 데이터 사용). 각 단계에 화면 ID·스크린숏·실제 입력 예시를 붙인다.

1. 아침 — 홈(SCR-HOME-01)에서 오늘 일정·남은 업무 보기. 빠른 입력(SCR-COM-02)으로 업무 추가.
2. 계획 — 캘린더 일·주 보기(SCR-CAL-01·02)에서 업무 패널(SCR-CAL-09)의 업무를 시간대로 끌어 놓기, 일정 빠른 생성(SCR-CAL-06), 반복 일정(SCR-CAL-07·08).
3. 일하는 중 — 업무 완료와 결과 한 줄(SCR-TASK-03), 직접 기록 추가(SCR-REC-01), 모바일 빠른 기록(SCR-MOB-01).
4. 일정이 끝난 뒤 — 확인 대기(SCR-HOME-02): 확인 / 수정 / 하지 않음 / 모두 했어요.
5. 하루 마감(SCR-LOG-03) — 하루 마감 시각 뒤 홈 띠, 알림(SCR-COM-05·SCR-SET-05), 3단계.
6. 돌아보기 — 일 보기 '이날의 기록', 업무 상세 기록 이력(SCR-TASK-02), 통계(SCR-STAT-01).
7. (옵션) 시간 기록을 켠 하루 — 타이머 미니 플레이어(SCR-COM-06), 이어달리기, 빈 시간 메우기(SCR-HOME-03).

## 4. 가상 데이터 시나리오(초안)

- 실제 기업명·프로젝트명을 쓰지 않는다. 이름은 확정 전에 웹 검색으로 실제 회사·제품과 겹치지 않는지 확인한다.
- 사용자: 가상 회사 '(주)가상예시상사'(이름 후보, 검색 확인 필요)의 마케팅팀 대리. 근무 09~18시, 월~금.
- 프로젝트 3개(색 다르게): '봄 신제품 소개 행사', '분기 고객 설문', '팀 운영'. 태그 4~5개: #보고 #회의 #디자인 #예산 #외부.
- 업무 15~20개: 상태가 고르게(할 일·진행 중·완료·보류), 마감 초과 1~2개, 오늘·이번 주 마감 몇 개, 진행률 있는 것, 보관한 것 1~2개(보관함 화면용).
- 일정: 반복 일정 2개(매주 월 09:30 팀 회의, 매일 17:30 메일 정리), 업무 연결 일정 하루 3~4개, 업무 없는 일정(외부 미팅) 1~2개, 종일 일정 1개.
- 기간: 통계가 의미 있게 보이려면 2주(근무일 10일) 이상. 아래 "확인 필요 ②"가 이 기간의 입력 방식을 정한다.
- 찍는 날: 확인 대기 2~3개가 남아 있고, 하루 마감 전 상태와 마감 후 상태를 모두 찍는다.

확인 필요(데이터를 넣기 전에):
- ① 숨김 뒤 '내일 계획'이 보이는 곳: 지금 이월은 일간 일지의 계획 항목에 들어간다(LOG-14). 일지를 숨기면 사용자는 다음 날 이 계획을 어디서 보는가. D-214 구현(PR #20)에서 정해진 모양을 WY-pm·WY-design에 확인하고 그 화면 기준으로 쓴다. 정해진 곳이 없으면 매뉴얼 이전에 결정 요청 거리다.
- ② 통계 기간: 통계의 완료 업무 수는 완료한 실제 시각(completed_at)으로 세고(StatsService), 기록 수는 기록 날짜(work_date)로 센다. 기록은 지난 날짜로 넣을 수 있지만 업무 완료는 넣는 날에만 찍힌다. 그래서 완료 추이를 보이려면 실제 날짜로 2주 동안 매일 조금씩 넣어야 한다. 지난 날짜 하루 마감이 되는지는 구현을 확인해야 한다. 운영 DB에 직접 넣는 방식은 쓰지 않는다(운영 데이터 직접 조작).

## 5. 환경·계정·정리

- 환경: 운영(wy-worklog.com). PR #20 배포 뒤.
- 계정: 매뉴얼 전용 운영 계정을 새로 만든다. 메일 인증을 마쳐야 미인증 배너(SCR-COM-07)가 찍히지 않는다. 인증번호는 사용자가 받아야 해서 사용자 할 일이 된다. 받는 주소는 저장소·문서에 적지 않는다.
- 가림: 계정 메일이 보이는 곳(설정 — 계정 SCR-SET-06, 프로필 등)은 찍지 않거나 가린다(D-206). 매뉴얼에는 계정 화면을 '예시 주소' 그림으로 대신할 수 있다.
- 정리: D-204처럼 유지 목록에 매뉴얼 계정을 올린다. 매뉴얼을 개정할 때 다시 찍어야 하므로 계정을 계속 둘지, 발행 뒤 지울지는 사용자 결정(7장).

## 7. 도구

- 후보 1 (지시안): app-docs(jezweb/claude-skills@app-docs, 미설치) + anthropic-skills:pdf. app-docs 원문은 아직 읽지 않았다. 설치 전에 내용을 읽어 브라우저 도구가 agent-browser와 맞는지, 무엇을 설치·실행하는지 확인해야 한다(설치는 사용자 승인).
- 후보 2 (추천): 새 스킬 없이 지금 쓰는 도구로. 스크린숏은 WY-qa가 agent-browser로 찍는다(이미 운영 QA에서 쓰는 방식, 화면 크기 지정·요소 가림 가능). 본문은 Markdown으로 쓰고, HTML 템플릿(인쇄 CSS, Pretendard 글꼴 포함)으로 묶어 headless Chrome 인쇄로 PDF를 만든다. 쪽 번호·목차·그림 번호는 인쇄 CSS로. anthropic-skills:pdf는 PDF 합치기·검사에만 쓴다.
  - 이유: 한글 조판·이미지 배치는 HTML 인쇄가 가장 손이 덜 가고, 화면 캡처는 이미 검증된 절차가 있다. 새 외부 스킬을 들이지 않는다.
  - 대가: 생성 스크립트를 하나 새로 만든다(docs/tools 쪽, 반나절). Chrome 인쇄는 브라우저를 띄우므로 메모리 확인 대상.
- 어느 쪽이든 원본(Markdown·이미지 목록·생성 스크립트)을 남겨 화면이 바뀌면 다시 찍고 다시 만든다.

## 9. 순서

1. 사용자 결정(10장) → 이 계획 확정.
