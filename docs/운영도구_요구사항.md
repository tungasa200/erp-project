## 1. 배경

승인 센터는 "대화창으로 요청하면 놓친다"는 문제를 풀려고 만들었다. 그런데 2026-10-06~07 운영에서도 사용자 손이 필요한 일이 계속 대화창에만 올라와 놓쳤다.

- 대화창에만 올라온 예: Vercel 2FA, 설정 파일 수정, VS Code 리로드, 권한 확인을 위한 attach, 명령 붙여 넣기
- 백그라운드 세션이 권한 확인에서 멈춘 것이 어디에도 보이지 않았다.
- 핵심 흐름이 불안정한 채로 패키지화(wy-ops)만 앞서 나갔다.

사용자 결정으로 운영 도구 작업을 모두 멈추고 요구사항부터 다시 정한다. 이 문서의 요구사항이 다음 작업의 기준이다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 승인 센터 | VS Code 확장의 작업창 탭. 사용자 손이 필요한 일을 카드로 모아 보여 주고 처리한다 |
| 카드 | 사용자에게 올리는 요청 하나. 종류는 권한 확인·결정·할 일·git 네 가지(OPS-02) |
| 요청 세션 | 카드를 올린 세션. 카드가 처리되면 결과를 받아 이어 간다 |
| 작업 흐름 | 서로 독립적으로 진행하는 작업 묶음. 담당 세션·목표·완료 조건을 가진다(OPS-05) |

## 3. 요구사항

### OPS-01 사용자 손이 필요한 일은 모두 카드로

사용자 손이 필요한 일은 전부 승인 센터에 카드로 올린다. 대화창 메시지는 "카드 올렸습니다" 알림으로만 쓰고, 처리 요청 자체를 대화창에만 두지 않는다. 처리하지 않은 카드는 쌓여서 남고, 처리되기 전까지 사라지지 않는다.

- 수용 기준: 세션이 사용자 손이 필요한 상황(외부 콘솔, 설정 수정, 리로드, 명령 실행, 결정, git 승인)을 만나면 승인 센터에 카드가 생긴다. 카드를 처리하지 않고 시간이 지나거나 새 카드가 와도 앞 카드는 목록에 남는다.

### OPS-02 카드 종류와 처리 방식

| 종류 | 언제 | 처리 방식 |
|---|---|---|
| ① 권한 확인 | 세션이 도구 실행 허용을 기다릴 때 | 승인 센터에서 바로 허용·거부한다. attach는 쓰지 않는다. Claude Code의 PermissionRequest 훅으로 구현한다(아래 "① 구현 방식과 한계") |
| ② 결정 | 세션이 진행 방향을 정해야 할 때 | 선택지 카드(choice). 선택지는 "누가, 어떻게 할지"만 고른다 |
| ③ 사용자가 직접 할 일 | 외부 콘솔 작업, 설정 파일 수정, 리로드, 명령 실행 | 할 일 카드에 방법 안내를 넣고 "했음" 버튼을 둔다. 누르면 요청 세션이 바로 이어 간다 |
| ④ git | 커밋·푸시 등 승인 대상 git 명령 | 지금의 승인 카드(승인·거부) |

① 구현 방식과 한계 (2026-10-07 조사 결과, 출처: https://code.claude.com/docs/en/hooks 의 PermissionRequest·Timeouts·PermissionDenied):

- 방식: PermissionRequest 훅은 확인 창이 뜰 때만 실행되고, 결정을 기다렸다가 allow/deny를 돌려줄 수 있다(기본 timeout 600초, 설정 가능). 백그라운드 세션에서도 실행된다.
- (a) deny 규칙과 auto 모드 분류기의 거부는 훅으로 뒤집을 수 없고, 뒤집어서도 안 된다. 이 두 경우는 ① 대신 ② 결정 카드나 ③ 할 일 카드로 보낸다. 예: 분류기에 막힌 WY-browser 시작은 사용자가 직접 실행하는 ③으로 처리한다.
- (b) 15분 동안 결정이 없으면 훅이 사유("승인 센터에서 15분 동안 결정 없음 — 다시 요청하거나 할 일 카드로")와 함께 거부를 돌려줘 닫는다(훅 timeout은 960초). 훅이 결정 없이 끝나면 확인 창으로 돌아가는데, 백그라운드 세션에는 답할 사람이 없어 무기한 멈추기 때문이다(실험 2026-10-07, D-90). 훅 오류도 허용이 아니라 거부·평소 흐름 쪽으로 닫힌다.
- (c) 허용은 그 한 번에만 적용한다. 영구 허용 규칙(updatedPermissions)은 쓰지 않는다.
- (d) 결정 파일의 키는 sha1(session_id · tool_name · tool_input JSON)의 앞 16자다(훅 입력에 tool_use_id가 없음, 실험 2026-10-07). 결정은 한 번 쓰면 used로 표시하고 다시 쓰지 않는다. 결정 파일 위조 방지(OPS-06 1)가 핵심 방어선이다.

예시 흐름(Vercel 2FA):

1. 세션이 2FA에서 막히면 ② 결정 카드가 뜬다. 선택지: 직접 처리 / Skip 허용 / 직접 설정.
2. "직접 처리"를 고르면 ③ 할 일 카드가 생긴다.
3. 사용자가 할 일을 마치고 "했음"을 누르면 세션이 이어 간다.

- 수용 기준: 네 종류 카드를 각각 하나씩 올려 처리했을 때 요청 세션이 결과(허용·거부, 고른 선택지, 했음, 승인·거부)를 받아 다음 동작으로 넘어간다. ③은 "했음"을 누른 뒤 사용자가 대화창에서 따로 알리지 않아도 세션이 이어 간다.
- 수용 기준(①): 백그라운드 세션이 권한 확인에 걸리면 승인 센터에 카드가 뜨고, 허용을 누르면 attach 없이 세션이 이어진다. 거부하면 사유가 세션에 전달된다. 15분 동안 결정이 없으면 세션은 사유가 담긴 거부를 받고 멈추지 않고 다음 행동으로 넘어가며, 승인 센터에 "시간 초과" 표시가 남는다. 같은 세션·도구·입력의 결정은 두 번 쓰이지 않는다. deny 규칙·분류기 거부는 ① 카드가 아니라 ②·③ 카드로 뜬다.

### OPS-03 카드만 보고 판단할 수 있다

카드에 무엇을, 왜, 선택지별 대가, 누르면 무슨 일이 일어나는지가 있다. 사용자가 대화창이나 다른 문서를 열지 않고 카드만 보고 처리할 수 있어야 한다.

- 수용 기준: 카드 형식에 위 네 항목 칸이 있고, 비어 있는 카드는 올라가지 않는다(요청 세션이 채우지 않으면 거부). 운영 중 대화창으로 되묻는 일이 생기면 결함으로 본다.

### OPS-04 멈춘 세션이 바로 보인다

권한 확인 대기처럼 멈춘 세션이 바로 보인다. 어떤 명령(도구와 인자)을 기다리는지까지 보여 준다. 세션에 들어가는(attach) 진입점은 세션 현황 대시보드 하나다 (D-89).

- 세션 현황 대시보드의 세션 줄마다 "열기" 버튼을 둔다. 누르면 VS Code 새 터미널에서 `claude attach <id>`가 실행된다.
- 권한 확인 대기와 사용자 입력 대기 세션은 줄에 색과 아이콘으로 구분해 표시한다. 구분은 `claude agents --json`의 waitingFor로 한다: permission prompt·sandbox request·worker request는 권한 대기, dialog open·input needed와 일을 마친 idle 세션은 입력 대기 (U-05 해소).
- 승인 센터의 권한 카드(OPS-02 ①)는 허용·거부로 끝난다. 카드에는 작은 링크 "세션 현황에서 보기"만 두고, attach 버튼은 두지 않는다.

- 수용 기준: 백그라운드 세션을 권한 확인에서 멈추게 하면 세션 현황에 그 세션이 권한 대기 색·아이콘과 기다리는 명령으로 표시되고, 세션이 다시 움직이면 표시가 사라진다. "열기"를 누르면 새 터미널에서 그 세션에 attach된다. 권한 카드의 "세션 현황에서 보기"를 누르면 세션 현황의 해당 줄로 간다.

### OPS-05 작업 흐름 단위 병렬

병렬은 독립된 작업 흐름 단위로 한다. 흐름마다 담당 세션, 목표, 완료 조건을 둔다. 정해진 순서는 세션끼리 직접 잇고, WY-pm은 흐름 사이 조율과 사용자 보고를 맡는다. 진행 현황은 흐름별 한 표로 본다.

- 수용 기준: 진행 현황 문서에 흐름별 표(흐름, 담당 세션, 목표, 완료 조건, 상태)가 있다. 한 흐름 안의 다음 단계는 WY-pm을 거치지 않고 앞 세션이 다음 세션에 직접 넘긴다.

### OPS-06 신뢰성이 기능보다 먼저

다음 네 가지를 지킨다. 새 기능보다 이 네 가지를 먼저 갖춘다.

1. 승인을 위조할 수 없다. 결정 파일(`decisions/`·`used/`)은 어떤 세션도 Edit·Write·셸 어느 쪽으로도 쓸 수 없다. 셸 차단은 휴리스틱이라 다른 스크립트를 불러 간접으로 쓰는 경우를 다 막지 못하므로, 확장이 남긴 기록(globalState)과 대조해 출처를 알 수 없는 결정 파일은 승인 센터에 경고 카드로 띄운다 (D-90).
2. 커밋 세션의 역할(`--agent WY-commit`)이 빠지면 감지한다.
3. 세션 재시작이나 VS Code 리로드 뒤에도 대기 카드와 상태가 남아 있다.
4. attach한 세션은 나온 뒤 --agent 없이 다시 뜰 수 있다. 커밋 전담 세션(WY-commit)을 "열기"로 열 때는 "나온 뒤 교대가 필요할 수 있음" 경고를 띄우고, 역할(agent)이 빠진 세션은 세션 현황 대시보드에 표시한다.

- 수용 기준: (1) 세션에서 Edit·Write·셸 명령(리디렉션, cp 등)으로 결정 파일 쓰기를 시도하면 거부된다. 간접 실행으로 만들어진 결정 파일은 "출처 불명" 경고 카드로 뜨고 그 결정은 쓰이지 않는다. (2) `--agent` 없이 띄운 커밋 세션은 승인 센터나 세션 목록에서 경고로 보인다. (3) 대기 카드가 있는 상태에서 VS Code를 리로드하고 세션을 다시 띄워도 같은 카드와 상태가 그대로 보인다. (4) WY-commit 줄에서 "열기"를 누르면 경고가 먼저 뜨고, attach 뒤 역할 없이 다시 뜬 세션은 세션 현황에 역할 누락으로 표시된다.

### OPS-07 패키지화는 안정화 뒤에

패키지화(wy-ops 6단계 이후)는 OPS-01~06이 이 프로젝트에서 안정된 뒤에 한다. 1~5단계는 커밋됐다(395f4c7까지). 6단계 도중의 미커밋 파일(tools/vscode-dashboard에서 tools/wy-ops/vscode, tools/wy-ops/ps로 옮기던 상태)은 지금 복구하지 않고 패키지화 때 그 시점의 커밋본에서 다시 한다(사용자 결정 2026-10-07, U-02 해소).

- 수용 기준: OPS-01~06의 수용 기준을 이 프로젝트 운영에서 모두 통과한 기록이 있기 전에는 wy-ops 6단계 이후 작업을 시작하지 않는다.
- 충족(D-92): OPS-01~06 수용 기준 통과 확인(2026-10-07) — 사용자 통합 확인(할 일 카드 20261007-1020 done: settings 적용·Reload·화면 확인), 권한 카드 왕복 시험(허용 1·거부 1, attach 없음, 1초 안에 이어짐), 카드 필수 칸 형식 오류 처리 a4b67a8, 출처 대조 9ae75c1, 역할 누락 판정 1c83943. OPS-08·09 화면은 배포됨(40428f4 이후).

### OPS-08 디자인

모던한 task 알림 도구처럼 만든다(참고: Linear 인박스, GitHub 알림).

원칙: 글로 읽는 화면이 아니라 GUI 도구답게 직관적으로 만든다. 상태·종류·진행은 색, 아이콘, 배지, 배치로 먼저 보이고, 글은 펼쳐서 읽는 상세에 둔다. 이 원칙은 승인 센터의 모든 화면(카드 목록·상세, OPS-04 멈춘 세션, OPS-09 세션 활동)에 적용한다 (D-88).

- 받은편지함 목록과 상세 보기
- 카드 종류별 아이콘·색
- 우선순위와 대기 시간 표시
- 한 번 클릭으로 처리
- 키보드 단축키
- 남은 개수 배지
- VS Code 라이트·다크 테마를 따름

목업: docs/운영도구/승인센터_목업.html (WY-design이 /impeccable로 작성 중).

- 수용 기준: 구현 화면이 목업과 위 일곱 항목을 갖추고, 라이트·다크 테마 모두에서 글자와 아이콘이 읽힌다. 카드를 펼치지 않고도 종류·우선순위·대기 시간을 알아볼 수 있다. WY-design이 목업과 대조해 확인한다.

### OPS-09 세션 활동 보기

배경: 세션을 VS Code 패널로 띄우던 때는 세션끼리 메시지를 주고받으며 오류를 찾고 고치는 모습이 바로 보였다. 백그라운드 세션으로 바꾼 뒤로는 사용자가 이를 볼 방법이 없다.

승인 센터에서 다음 세 가지를 본다. 화면은 OPS-08 원칙(GUI 직관성)을 따른다.

1. 세션 간 메시지: 누가, 누구에게, 무엇을 보냈는지 시간 순서 피드로 본다. 처음에는 요약만 보이고 한 번 클릭으로 원문을 펼친다.
2. 세션 상태: 세션마다 지금 하는 일과 상태(일하는 중 / 대기 / 권한 확인 대기 / 멈춤)를 본다. 상태는 색과 아이콘으로 구분한다. 권한 확인 대기는 OPS-04와 같은 정보(기다리는 명령)로 이어진다.
3. 결함 흐름 묶음: 오류를 찾고 고치는 흐름(보고 → 수정 → 재검증)을 하나의 묶음으로 모아 단계별 진행을 본다.

데이터 출처: 세션 대화 기록(~/.claude/projects/<프로젝트>/*.jsonl)과 `claude agents --json`의 상태. 받은 메시지는 `origin.kind: "peer"`(보낸 세션·msg_id·본문) 줄, 보낸 메시지는 SendMessage `tool_use`(to·summary·message)로 읽는다. 대화 기록 형식은 공개 계약이 아닌 내부 형식이라 Claude Code 업데이트로 바뀔 수 있고, 바뀌면 활동 보기를 고친다 (U-04 해소). 활동 보기는 우선 승인 센터와 별도 탭으로 만들고, 합칠지는 디자인 단계에서 정한다 (D-90).

- 수용 기준: 두 세션이 메시지를 주고받으면 10초 안에 피드에 보이고, 한 번 클릭으로 원문을 펼친다. 권한 확인 대기 세션은 다른 상태와 색·아이콘으로 구분된다. 한 결함의 보고·수정·재검증 메시지가 같은 묶음 안에 순서대로 보인다.

### OPS-10 패키지화

사용자가 패키지화를 다음 일로 정했다(2026-10-07). 지난번에는 요구사항 없이 단계부터 진행했다가(wy-ops 6단계, 되돌림) 요구사항을 다시 정의했으므로, 이번에는 이 요구사항을 확정한 뒤 구현한다. 이전 계획 tools/PACKAGING-PLAN.md의 1~5단계(설정 파일, 설정 읽기, 프로젝트별 승인 폴더, 역할 파일 생성기, pm-ops 분리)는 커밋된 상태이고, 6단계(패키지 추출·install.ps1·확장 id 변경) 이후를 이 요구사항에 맞춰 다시 계획한다.

목적은 두 가지다.

1. 같은 프로젝트를 다른 PC에서 이어 간다. 다른 PC에서 빠르게 세팅해 지금 이 PC와 똑같이 운영 도구를 쓴다.
2. 다른 프로젝트를 새로 시작할 때 이 작업 환경을 빠르게 적용한다.

범위 (D-91):

- 패키지는 이 저장소 `tools/`에서 계속 개발한다. P4 이후 최종 작업을 마무리한 뒤 별도 저장소로 분리한다. 그때까지 새 프로젝트(목적 2)는 이 저장소의 `tools/`에서 설치한다.
- 지원 OS는 Windows만이다.
- 메모리 폴더는 다른 PC로 옮기지 않는다. 기준 규칙은 CLAUDE.md·docs에 있다.
- 사용자 전역 지침(`~/.claude/CLAUDE.md`)과 개인 스킬(`~/.claude/skills/`)은 패키지에 넣지 않고 새 PC 체크리스트로 안내한다.

#### OPS-10-1 다른 PC에서 같은 프로젝트 이어 가기

새 PC에서 저장소를 clone한 뒤 정해진 짧은 절차로 승인 센터·세션 현황·활동 보기·훅·역할 세션이 이 PC와 같이 동작한다. 저장소에 없는 것(6장 표)은 절차가 다시 만들거나, 무엇을 손으로 옮길지 목록으로 알려 준다.

- 전제: 6장 "새 PC 전제"의 도구(Windows 10 이상, PowerShell 5.1, Git, Node, VS Code, Claude Code CLI)가 설치되어 있고 사용자가 Claude Code에 로그인했다.
- 수용 기준:
  - clone 뒤 설치 명령 3개 이내와 VS Code 리로드 1회로 끝난다. 설치 명령이 손으로 할 일을 남기면 체크리스트로 출력하고, 승인 센터가 뜬 뒤에는 남은 일을 ③ 할 일 카드로 올린다.
  - 점검 명령(doctor)이 통과한다: 훅 5종(승인 가드, 메시지 가드, 권한 확인, 권한 거부, 세션 시작)의 경로에 파일이 있고, 필요한 플러그인·확장·승인 폴더가 있으며, 설치본 버전이 저장소의 버전과 같다.
  - 시험 세션으로 네 종류 카드(OPS-02)를 한 번씩 왕복하고, `--agent`로 역할 세션 하나를 띄워 세션 현황·활동 보기에 보인다.
  - 개인 경로(사용자 홈 등)는 그 PC에서 계산해 넣는다. 다른 PC의 경로가 설정 파일에 남지 않는다.
  - 다른 PC로 옮기지 않는 것(승인 대기열, 대화 기록, 인수인계 파일)은 문서에 적혀 있고, 옮기기 전에 할 일(진행 중 카드 처리, 작업 경계에서 멈추기)이 절차에 있다.

#### OPS-10-2 새 프로젝트에 작업 환경 적용

새 프로젝트 폴더에서 init 한 번으로 운영 도구에 필요한 프로젝트 파일이 생긴다.

- 생기는 것: `.claude/wy-ops.json`(프로젝트 이름·역할 목록·pm·커밋 역할·승인 namespace), 역할 원본 `.claude/ops/`와 생성된 `.claude/agents/*.md`, pm-ops 스킬(코어 + 프로젝트 부록), `.claude/settings.local.json`의 훅·deny 조각, 승인 폴더 `~/.claude/wy-approvals/<namespace>/`, `.gitignore` 항목(local 설정 파일).
- 수용 기준:
  - 빈 시험 프로젝트에 init을 실행하면 위 파일이 생기고 doctor가 통과한다.
  - 그 프로젝트에서 세션 하나를 띄워 결정 카드 1회, git 승인 카드 1회가 끝까지 동작한다.
  - 두 프로젝트(이 프로젝트와 시험 프로젝트)의 승인 대기열·세션 현황·활동 보기가 섞이지 않는다.
  - 이미 있는 파일(CLAUDE.md, 기존 settings.local.json의 다른 키 등)을 덮어쓰지 않는다. 병합할 것은 차이를 보여 주고 확인받는다. CLAUDE.md는 자동으로 고치지 않고 넣을 내용을 출력한다.

#### OPS-10-3 공통 조건

- 이 프로젝트는 패키지화 작업 중에도 지금처럼 돌아간다. 단계마다 되돌릴 수 있고, 훅 경로를 바꾸는 단계는 새 경로에 파일이 있는 것을 doctor로 확인한 뒤 바꾼다(경로가 틀리면 훅이 조용히 통과해 OPS-06이 깨진다).

## 7. 사용자 손을 줄이는 방향 (OPS-10)

- 설정 파일(D-87): 세션은 설정 파일을 직접 고치지 않는다. 사용자가 실행하는 설치·업데이트 명령이 템플릿에서 생성·병합하고 차이를 보여 준 뒤 쓰게 하면, 사람이 파일을 손으로 고칠 일이 없어진다. 세션이 설정 변경이 필요하다고 판단하면 ③ 할 일 카드에 "설치 명령 한 줄 실행"을 올린다.
- 확장 설치: 확장 id 변경은 한 번에 끝내고(PACKAGING-PLAN D5), 이후에는 설치본 경로만 바꿔 재설치 없이 리로드로 업데이트되게 한다.
- 플러그인: 목록을 저장소에 두어 설치 명령이 한 번에 설치하거나, 설치할 명령을 그대로 복사할 수 있게 출력한다.
- 로그인(Claude Code, GitHub, 외부 콘솔): 자동화할 수 없으므로 체크리스트에 두고, doctor는 확인할 수 있는 것만 확인한다.
- 남은 손일은 대화창이 아니라 승인 센터 ③ 할 일 카드로 올린다(OPS-01). 승인 센터가 뜨기 전 단계의 일은 설치 명령의 체크리스트 출력으로 안내한다.
- 점검 하나로 끝낸다: doctor가 6장 항목 중 확인할 수 있는 것을 모두 보고, 실패마다 고치는 방법 한 줄을 보여 준다.
