## 2. 시험 계정

- 새 계정 1개(P, perf)를 만든다. 주소는 기존 시험 계정처럼 사용자 Gmail의 별칭(`+perf` 꼴)을 쓴다. 주소·비밀번호는 문서·메시지·커밋에 적지 않는다.
- 가입은 메일을 보내지 않는다. 가입하면 바로 로그인되고 이메일 인증은 막지 않는다(contracts/identity.yaml signup, D-20). 따라서 사용자의 메일함 작업은 없다. 인증 메일 발송 API는 부르지 않는다. 미인증이면 막히는 것은 내보내기뿐이고, 내보내기는 측정 대상이 아니다.

## 4. 넣는 방법

- 앱과 같은 공개 API를 쓴다. 스크립트는 Node fetch로 `https://wy-worklog.com/api/...`를 호출한다. 앱처럼 Origin 헤더와 쿠키를 붙인다.
  - `POST /api/auth/signup`(1회) → `POST /api/worklog/projects`·`tags`·`tasks`·`schedules`·`records` → `POST /api/worklog/logs/daily/{date}/close`
- 요청 제한:
  - 로그인 보호(IP당 1분 10회 실패)는 실패만 세므로 로그인 1회면 해당이 없다.
  - worklog API에는 일반 요청 제한이 없다. 그래도 운영 부담을 줄이려고 동시 2개, 초당 5건 이하로 넣는다(약 3,500건, 15분 안팎).
- access token은 최대 10분이라 401이 나면 `/api/auth/refresh`를 한 번 부르고 이어 간다.
- 실패한 요청은 traceId와 함께 run 파일에 남긴다. 5xx가 1%를 넘으면 멈추고 `[차단]`한다.

## 5. 측정 방법

공통 조건:

- 측정기: 이 PC에서 운영 주소로 요청한다(한국 → Vercel → Railway 싱가포르, 실제 사용자 경로). 시간은 요청 시작부터 응답 본문을 다 받을 때까지(Node `performance.now`)다.
- 측정은 데이터 넣기가 끝나고 5분 뒤에 한다. API마다 예열 5회 뒤 100회를 차례로 부른다(동시 요청 없음, 부하 시험 아님).
- p95는 100개를 정렬한 95번째 값이다. 중앙값·최대값도 함께 적는다.
- 배포·재시작 직후는 피한다. 측정 시각과 운영 커밋(release)을 적는다.

### 5.1 일반 조회 API(p95 500ms)

| API | 조건 |
|---|---|
| GET /api/users/me, /api/worklog/me | |
| GET /api/worklog/tasks | 기본(진행 중·할 일, sort=due), 완료 필터 |
| GET /api/worklog/tasks/frequent | |
| GET /api/worklog/schedules | 2026-10 한 달(월 보기), 한 주(주 보기), 하루 |
| GET /api/worklog/records | 하루, 한 달(2026-09) |
| GET /api/worklog/records/pending | |
| GET /api/worklog/logs | DAILY 한 달, WEEKLY |
| GET /api/worklog/logs/DAILY/{오늘} | 홈 오늘 일지 카드 |
| GET /api/worklog/stats, /stats/plan-vs-actual | 이번 달, 최근 3개월 |
| GET /api/worklog/notifications | limit=1(배지) |

- 각 API의 p95가 500ms를 넘으면 결함으로 등록한다(WY-backend2).
- 네트워크 몫을 가르려고 서버 처리 시간도 함께 본다. 미달 API만 WY-browser가 gateway 로그(traceId)에서 서버 시간을 확인한다.

### 5.2 월간 일지 생성(3초)

- `GET /api/worklog/logs/MONTHLY/2026-09`는 저장 전 미리보기라 부를 때마다 원본으로 다시 만든다(계약 getLog). 20회 불러 최대값과 p95가 3초 이내인지 본다.
- 화면에서도 일지 › 월간 2026-09를 열어 본문이 보일 때까지 걸리는 시간을 5회 잰다(Playwright, 1280).

### 5.3 하루 마감(60초)

- 2026-10의 한 근무일(확인 대기 5건, 이월 후보 10건 이상)을 마감한다. 5회 반복하며, 매번 다른 날로 한다.
- 화면 경로: 홈 [하루 마감] → 확인 대기 처리 → 이월 → 확정. 스크립트로 조작해 첫 클릭부터 "일지를 확정했어요"까지의 시간을 잰다.
  - 사람의 입력 시간은 빼므로, 기준은 "화면 대기 합계 + 단계 수"로 판단한다.
- API(`GET .../close`, `POST .../close`)의 시간도 따로 적는다.

### 5.4 캘린더(추천: WY-frontend2)

- WY-frontend2가 Chrome 성능 탭(Performance trace)으로 2026-10 월 보기·주 보기의 첫 렌더링, 보기 전환, 일정 드래그를 잰다.
  - 긴 작업(50ms 넘는 Long Task) 수, 프레임 시간을 본다.
  - 같은 측정을 CPU 4배 감속으로도 한다.
- 빌드 번들 크기(`vite build` 결과)도 WY-frontend2가 적는다.
- WY-qa는 계정·데이터를 넘겨주고 결과를 시트에 합친다(결정 요청 ②).
